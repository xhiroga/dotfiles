# issue tree

1 つの目的から始めた作業が、調べるうちに別の課題を見つけて枝分かれしていくと、会話を追うだけでは「何が終わって何が残っているか」が分からなくなる。そうなったら全体を木にして、会話の外 (課題管理) に置く。

## いつ使うか

- 派生が 2 段以上になったとき (目的 → 見つかった原因 → その原因の対応、のように)
- 人に「何が残っているか」を見せるとき
- 別のセッションと作業を分け合っていて、どちらの担当かを書き分けたいとき

## 置き場

- 代表 issue の説明 (description) の先頭。代表 issue は当初の目的に当たる issue。元の本文は `---` の下に残す
- 課題管理が Linear と GitHub Issues の両方にあるときも、代表は Linear に置く
- 代表 issue が見つからないときは、立てる前に聞く
- 会話には木を貼り直さない。変わった枝だけを言い、木そのものは issue で見てもらう

## 状態の記号

| 記号 | 意味 | Linear の状態 |
|---|---|---|
| ✅ | 済 | Done |
| 🚧 | 途中 | In Progress |
| ⬜ | 未 | Backlog / Todo |
| ⏳ | 待ち (方針・他の人・外部の処理) | (Blocked にあたる) |
| ❌ | やめた | Canceled |

- 🚧 はコミットの絵文字の慣習 (gitmoji) でも「作業中」。🔄 は「更新した・同期・繰り返し」と読まれるので「途中」に使わない
- ❌ は決めて捨てた案にも使い、理由を添えて木に残す。後から同じ案を蒸し返さないため
- 「次にやること」は状態ではなく優先順位なので記号にしない。木の上に番号付きで 2〜5 行並べる
- 子 issue があるノードは、記号をその issue の状態と揃える。枝が済んだら子 issue も完了コメントを付けて閉じる

## 書き方

````
## Issue tree (YYYY-MM-DD HH:MM JST 更新)

✅ 済 / 🚧 途中 / ⬜ 未 / ⏳ 待ち / ❌ やめた

次にやること

1. <いちばん先にやること> (<止まっている理由があれば>)
2. ...

```
<当初の目的> (<代表 issue>、<始めた日>)
│
├─ 🚧 A. <枝>
│   ├─ ❌ <採らなかった案> (<理由>)
│   ├─ ✅ <済んだこと>。<コミット・日付・件数>
│   └─ ⬜ <残り> (<担当が別なら書く>)
│
└─ 🚧 D. 派生
    ├─ ⏳ <待っていること> (<何を待っているか>)
    └─ ⬜ <派生した課題> (<issue 番号> または「未起票」)
```
````

- 木はコードブロックに罫線 (├─ │ └─) で書く。入れ子のリストより枝の深さが見える
- 1 行は「記号 + 何をしたか + 根拠」。根拠はコミット・日付・件数など、後から確かめられるもの
- 人や作品のように状態を持たない区切りのノードには記号を付けず、その下に状態を持つ行をぶら下げる
- 別のトラッカーの issue は `<repo>#NNN` と書く。issue でない番号 (シートの行など) には `#` を付けない (課題管理が issue へのリンクにしてしまう)

## 更新

- 状態が変わったら木を書き換え、見出しの更新時刻を変える。Linear MCP なら `save_issue` の `patch` で、`replace_range` (from = 見出しの行、to = 元の本文の先頭) を使って木だけ差し替える
- ✅ は確かめてから付ける。本番に出たか・数字が合ったかを見ずに、作業を終えただけで付けない
- 見直して誤りが分かった枝は直し、会話でも前回の誤りとして伝える
